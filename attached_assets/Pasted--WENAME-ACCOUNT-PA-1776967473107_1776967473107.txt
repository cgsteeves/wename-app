PART 1 — USER IDENTITY MODEL
================================================================================

WeName uses a TWO-TABLE identity model:

  TABLE 1: auth.users (Supabase-managed)
    The authentication identity. Supabase writes and owns this table.
    Never written to directly from app code.
    auth.users.id is the canonical, permanent user ID.
    Contains: id (uuid), email, provider, created_at, user_metadata (name from OAuth)

  TABLE 2: public.users (App-managed)
    The app profile table. id MUST equal auth.users.id.
    Written to via upsert after every successful auth event.
    This is the row the entire app reads for all user data.

    Relevant columns for auth:
      id           uuid    PK  — always equal to auth.users.id
      email        text    nullable — synced from auth on sign-in
      display_name text    nullable — set from OAuth metadata or user input
      invite_code  text    — 8-char random code, generated on first use
      updated_at   timestamptz

GUEST MODE IDENTITY:
  Before signing in, the app creates a row in public.users with a random UUID
  (different from any auth.users.id). This UUID is stored in localStorage as
  'baby_picker_user_id'. Guest users have full app functionality except:
    - Data is saved on the current device only
    - Cannot invite partner via link (only via code)
    - Data will be lost if localStorage is cleared

AUTHENTICATED MODE IDENTITY:
  After sign-in, auth.users.id becomes the canonical ID.
  The localStorage key 'baby_picker_user_id' is updated to the auth user ID.
  Guest data is migrated from the old guest UUID to the new auth UUID.

PART 4 — GOOGLE OAUTH FLOW (END TO END)
================================================================================

ENTRY POINTS:
  - AccountPage "Continue with Google" button
  - AuthModal "Continue with Google" button in 'choose' mode

STEP 1: Initiation
  signInWithGoogle() calls:
    supabase.auth.signInWithOAuth({
      provider: 'google',
      options: { redirectTo: '{window.location.origin}/auth/callback' }
    })
  This causes a FULL PAGE NAVIGATION to Google's OAuth consent screen.
  The user is taken entirely away from the app.

STEP 2: Google OAuth
  User authenticates with Google (selects account, grants permissions).
  Google redirects to Supabase's OAuth endpoint.

STEP 3: Supabase Exchange
  Supabase exchanges the authorization code for a session.
  Supabase redirects to {origin}/auth/callback with session tokens in URL.

STEP 4: AuthCallback
  App.tsx detects the /auth/callback route and renders AuthCallback.
  Supabase JS client automatically parses the URL and sets the session.
  AuthCallback calls supabase.auth.getSession() to confirm the session.
  If session not found after initial check: waits 800ms and tries again.
  Once session confirmed: calls finalizeLogin(userId, email).

STEP 5: finalizeLogin (see Part 6 for full details)

STEP 6: Post-auth redirect
  consumePostAuthRedirect() checks localStorage for a pending redirect key.
  If found (e.g., 'partner'): redirects to '/?redirect=partner'
  If not found: redirects to '/'
  Uses setTimeout 1000ms before redirect (so AuthCallback success state is visible briefly)
  Uses window.location.replace() so the /auth/callback URL is removed from history.

PART 5 — EMAIL MAGIC LINK FLOW (END TO END)
================================================================================

ENTRY POINTS:
  - AccountPage email form
  - AuthModal email mode

STEP 1: User submits email
  signInWithEmailMagicLink(email) is called from the app.
  This calls the send-magic-link Edge Function:

    POST {SUPABASE_URL}/functions/v1/send-magic-link
    Headers:
      Content-Type: application/json
      Authorization: Bearer {SUPABASE_ANON_KEY}
      Apikey: {SUPABASE_ANON_KEY}
    Body: { email: "user@example.com", redirectTo: "{origin}/auth/callback" }

STEP 2: Edge Function — send-magic-link
  Runs on Deno runtime (Supabase Edge Functions).

  Uses the Service Role Key to call Supabase Admin API:
    supabaseAdmin.auth.admin.generateLink({
      type: 'magiclink',
      email: email.trim().toLowerCase(),
      options: { redirectTo: redirectTo || 'https://wename.app/auth/callback' }
    })

  This generates a magic link that looks like:
    https://[project].supabase.co/auth/v1/verify?token=...&type=magiclink&redirect_to={redirectTo}

  Then sends a branded HTML email via SendGrid:
    POST https://api.sendgrid.com/v3/mail/send
    Authorization: Bearer {SENDGRID_API_KEY}
    From: admin@wename.app (name: "WeName")
    Subject: "Log in to WeName"
    Content: branded HTML email + plain text fallback

  EMAIL DESIGN:
    Background: parchment #f2ead8
    Card: #ece4d0 with warm border and subtle shadow
    Logo image from Supabase Storage
    Heading: "Sign Up or Log In" — bold, dark brown
    Body text: warm gray, explains link is magic/passwordless, expires in 10 minutes
    CTA button: blue (#2e6aad), pill-shaped (border-radius 999px), "Log In"
    Fallback link: same URL shown in plain text below CTA
    Footer: "If you didn't request this email, you can safely ignore it."

  If SendGrid or link generation fails: returns 500 with { error: "..." }
  On success: returns 200 with { success: true }

STEP 3: User taps link in email
  The magic link in the email routes to:
    https://[supabase].supabase.co/auth/v1/verify?token=...
  Supabase verifies the token and redirects to:
    {origin}/auth/callback

STEP 4: AuthCallback handles the session
  Identical to Google OAuth Step 4 and beyond (see Part 4).

LINK EXPIRY:
  The Edge Function email body says "expires in 10 minutes."
  The AuthModal email-sent screen says "expires after 1 hour."
  The actual expiry is configured in Supabase project settings.
  These messages should be made consistent to match the actual setting.

PART 6 — FINALIZE LOGIN (POST-AUTH PROFILE UPSERT)
================================================================================

finalizeLogin(userId: string, email: string) is called by AuthCallback
after EVERY successful authentication event (any provider).

Steps in order:

  1. Build updates object:
     { id: userId, updated_at: now().toISOString() }
     If email is truthy: add email to updates.

  2. Fetch existing profile from public.users:
     SELECT display_name, invite_code FROM users WHERE id=userId
     (maybeSingle — no error if not found)

  3. If no display_name in existing profile:
     Fetch auth metadata: supabase.auth.getUser()
     Check user_metadata.full_name or user_metadata.name
     If a name is found in metadata: add display_name to updates.
     (This populates the display name from Google's profile for new OAuth users.)

  4. If no invite_code in existing profile:
     Generate a new invite_code: Math.random().toString(36).substring(2,10).toUpperCase()
     Add to updates.

  5. Upsert into public.users:
     INSERT INTO users (...updates) ON CONFLICT (id) DO UPDATE SET ...
     Uses ignoreDuplicates: false so all fields are always updated.

  6. Guest data merge:
     const guestUserId = localStorage.getItem('baby_picker_user_id')
     If guestUserId exists AND guestUserId !== userId:
       await mergeGuestData(guestUserId, userId)
     (See Part 7 for full merge details)

  7. Update localStorage:
     localStorage.setItem('baby_picker_user_id', userId)
     (useUser() will now load this auth user profile on next read)

================================================================================
PART 7 — GUEST DATA MERGE
================================================================================

mergeGuestData(guestUserId, authUserId) runs during finalizeLogin.
Called only when the stored guest ID differs from the auth user ID.
This means a user who was using the app as a guest before signing in
will not lose their data.

Three operations run in order:

OPERATION 1 — mergeSwipes:
  SELECT name_id, liked FROM swipes WHERE user_id=guestUserId
  SELECT name_id FROM swipes WHERE user_id=authUserId
  Build a Set of name_ids already swiped by auth user.
  Filter guest swipes: keep only those NOT already in the Set.
  INSERT INTO swipes (user_id=authUserId, name_id, liked) for each filtered row.
  Conflict avoidance: duplicate name_ids are explicitly filtered before insert.

OPERATION 2 — mergeMatches:
  UPDATE matches SET user_a_id=authUserId WHERE user_a_id=guestUserId
  UPDATE matches SET user_b_id=authUserId WHERE user_b_id=guestUserId
  (Reassigns all match rows to the auth user ID)

OPERATION 3 — mergeProfileSettings:
  Reads both profiles (guestUserId and authUserId).
  Only writes if the AUTH profile is missing a value:
    display_name:        copy if auth has none, guest has some
    baby_last_name:      copy if auth has none, guest has some
    baby_gender:         copy if guest has a non-'either' value
    partner_id:          copy if auth has no partner, guest does
    invite_code:         copy if auth has no invite_code
    onboarding_complete: copy if auth hasn't completed
    plan_tier:           copy if auth has no plan tier
  If any fields to write: UPDATE users SET {...} WHERE id=authUserId

ERROR HANDLING:
  The whole mergeGuestData function is wrapped in try/catch.
  Errors are logged but DO NOT fail the login flow.
  The user signs in successfully even if merge partially fails.

PART 8 — DELETE ACCOUNT FLOW
================================================================================

There are TWO deletion paths:

PATH A: In-app deletion (authenticated user, from AccountPage)
  Requires: isAuthenticated=true and a valid session

  Client-side:
    deleteAccount() from AuthContext → authDeleteAccount() from authService:
      1. Get current session: supabase.auth.getSession()
         If no session: throw Error('Not authenticated')
      2. POST to delete-account Edge Function:
         Authorization: Bearer {session.access_token}
         (Uses user's own JWT — not the anon key)
      3. On success: localStorage.removeItem('baby_picker_user_id')
                     localStorage.removeItem('post_auth_redirect')
                     await supabase.auth.signOut()
      4. AuthContext sets session = null → app shows Guest Mode

  Edge Function (delete-account):
    Verifies the user JWT (not service role) to authenticate the request.
    Creates two clients: one for auth (service role), one for user verification (anon+JWT).
    Calls userClient.auth.getUser() to confirm identity from the JWT.

    Then using the admin client:
    1. SELECT partner_id FROM users WHERE id=userId
    2. If partner_id exists:
         UPDATE users SET partner_id=null WHERE id=partner_id
         (Clears the partner's backlink so they don't have a dangling reference)
    3. DELETE FROM users WHERE id=userId
       (Cascade deletes swipes and matches via FK constraints)
    4. supabaseAdmin.auth.admin.deleteUser(userId)
       (Removes the auth.users row — full identity deletion)
    5. Return { success: true }

  On error from Edge Function:
    setDeleteError(error.message)
    The user remains signed in and the page shows the error.

PATH B: External deletion request (unauthenticated, from /delete-account route)
  For users who have forgotten their login or can't access the app.
  Accessible at: https://wename.app/delete-account (standalone page, not in Settings)

  Page: DeleteAccountPage (rendered from App.tsx when path === '/delete-account')
  Uses AuthContext to detect if signed in.

  If AUTHENTICATED (isAuthenticated=true): shows AuthenticatedView
    Shows current email ("Signed in as")
    Two-step confirmation:
      Step 1 (idle): "Delete My Account" button (destructive/5 bg, light red)
        On press: setStep('confirm')
      Step 2 (confirm): Warning card + Cancel + "Yes, Delete" buttons
        Cancel: setStep('idle')
        "Yes, Delete": calls deleteAccount() (same as above)
    On success: setDeleted(true) → shows "Account Deleted" confirmation screen

  If NOT AUTHENTICATED (isAuthenticated=false): shows UnauthenticatedView
    Shows "What gets deleted" list:
      - Your profile and account credentials
      - All name swipe history (likes and dislikes)
      - All name matches with your partner
      - Any custom names you created
      - Your partner link (your partner's account is not affected)

    Form with:
      Email input (required, validated)
      Reason textarea (optional, max 1000 chars)
      "Submit Deletion Request" button (bg-destructive, white)

    On submit:
      POST {SUPABASE_URL}/functions/v1/submit-deletion-request
      Headers: Apikey only (no Authorization needed — unauthenticated request)
      Body: { email, reason? }
      On success: shows "Request Received" confirmation:
        CheckCircle2 icon, green
        "We'll process your deletion request within 30 days and send a confirmation to {email}."
      On error: shows error below form

  After deletion (deleted=true):
    Full-screen confirmation:
      CheckCircle2 icon (size 32, green-600)
      "Account Deleted" — Fredoka bold, size 18 (text-lg)
      "Your account and all associated data have been permanently removed."
      "Return to WeName" link (href="/", sky-600, underline, ExternalLink icon)

PART 10 — AUTH CONTEXT
================================================================================

AuthProvider wraps the entire app (and standalone page routes that need auth).

State managed:
  session:         Session | null  — the full Supabase auth session
  authLoading:     boolean         — true until first getSession() resolves
  showAuthModal:   boolean         — for future global modal trigger (currently unused in app)

On mount:
  supabase.auth.getSession() → sets session, authLoading=false
  supabase.auth.onAuthStateChange() subscription:
    On SIGNED_IN or USER_UPDATED with a session:
      Upsert {id, email} into public.users (lightweight backstop)
      Full profile upsert happens in finalizeLogin via /auth/callback
    On any event: setSession(newSession)

Exposed values:
  session:          Supabase Session object (has .access_token, .user, etc.)
  authUser:         session?.user — Supabase User object (has .id, .email, .user_metadata)
  isAuthenticated:  !!session  — boolean shorthand
  authLoading:      boolean
  showAuthModal:    boolean
  openAuthModal():  sets showAuthModal=true
  closeAuthModal(): sets showAuthModal=false
  signOut():        calls authSignOut() + setSession(null)
  deleteAccount():  calls authDeleteAccount() + setSession(null)

useAuth() hook:
  Calls useContext(AuthContext)
  Throws if used outside AuthProvider: 'useAuth must be used within AuthProvider'

IMPORTANT: The AccountPage does NOT use AuthContext.openAuthModal().
It manages its own auth state directly (googleLoading, emailLoading, emailSent, etc.)
and calls signInWithGoogle() / signInWithEmailMagicLink() directly.
The AuthModal is a separate component used for inline overlay presentation.

================================================================================
PART 12 — SESSION PERSISTENCE
================================================================================

Supabase JS client persists the session automatically in localStorage.
On app load, supabase.auth.getSession() reads from localStorage and
re-hydrates the session without any network request.
Sessions are refreshed automatically by the Supabase JS client.
No manual token refresh logic is needed.

localStorage keys used by the app (separate from Supabase's own keys):
  'baby_picker_user_id'   — stores the user's public.users UUID
  'post_auth_redirect'    — optional pending redirect destination after auth
  'onboarded'             — whether the user has completed onboarding

Supabase's own localStorage keys (managed by the JS client, not touched by app code):
  'sb-{projectRef}-auth-token'  — the JWT session (handled automatically)
