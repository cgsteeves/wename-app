================================================================================
PART 1 — ARCHITECTURE OVERVIEW
================================================================================

The Partner page lives inside the Settings stack and has two conceptual layers:

  LAYER 1: PartnerPage
    The main Settings sub-page. Controlled by activePage='partner' in SettingsPage.
    Has an internal sub-view state:  subView: 'main' | 'invite'

    'main' renders the main partner UI (either connected state or unconnected state).
    'invite' renders InvitePartnerView inline (same scroll area, same back header).

  LAYER 2: JoinView (separate from PartnerPage)
    A standalone full-screen page shown when the user opens a /join/{token} URL.
    This is NOT inside the Settings stack.
    It is rendered from App.tsx by detecting the /join/:token URL path pattern.

These two layers share the same backend RPC (accept_partner_invite) but are
entirely separate UI components with separate state.

PART 6 — AUTH GATE FOR INVITE (PENDING INVITE REF PATTERN)
================================================================================

When the user taps "Invite Partner" and is NOT authenticated:

  setPostAuthRedirect('partner')
    Writes 'partner' to localStorage key: 'post_auth_redirect'

  pendingInviteRef.current = true
    An in-component ref (NOT state) — avoids stale closure issues

  setShowAuthModal(true)
    Opens the AuthModal inline (overlaid on the Partner page)

  AuthModal receives:
    preHeader: "You're one step away from matching together"
    title: "Invite your partner & start matching"
    body: "Create your account to share your link and instantly see your matches together."

  When AuthModal is closed (user dismisses without signing in):
    setShowAuthModal(false)
    pendingInviteRef.current = false
    (nothing else happens — user stays on Partner page)

  When authentication COMPLETES (isAuthenticated changes to true):
    A useEffect watches [isAuthenticated]:
      if (isAuthenticated && pendingInviteRef.current) {
        pendingInviteRef.current = false
        setShowAuthModal(false)
        setSubView('invite')   ← navigates to InvitePartnerView
      }

  The AuthModal is rendered OUTSIDE the main page div (sibling, not nested inside):
    It conditionally renders at the TOP of the PartnerPage return, before the main div.
    This means it overlays the entire settings stack visually.

  The showAuthModal boolean lives in the PartnerPage component state and is separate
  from the global AuthContext.showAuthModal. They are different modals.

  IMPORTANT: Once the user is authenticated, visiting the Partner page again will
  immediately show the InvitePartnerView without auth gating — the gate only fires
  for guest users.

PART 7 — INVITE PARTNER VIEW (INVITE LINK + SHORT CODE)
================================================================================

Rendered when subView='invite'.
Has its own SubPageHeader with title "Invite Partner" and onBack → setSubView('main').

--- ON MOUNT ---

generate() is called immediately via useEffect([userId]).

generate() steps:
  setLoading(true), setError('')
  Call createInvite(userId):
    1. Expire all existing pending invites for this user:
       UPDATE partner_invites SET status='expired'
       WHERE inviter_id=userId AND status='pending'
    2. Generate a cryptographically random token (48 hex chars):
       crypto.getRandomValues(24 bytes) → hex string
    3. Generate a human-readable short code (8 chars, uppercase alphanumeric):
       Character set: ABCDEFGHJKLMNPQRSTUVWXYZ23456789
       (Note: no O/0, no I/1 to avoid visual confusion)
       crypto.getRandomValues(8 bytes) → each byte maps to a char
    4. INSERT INTO partner_invites (token, short_code, inviter_id, status='pending')
       expires_at defaults to now() + 7 days
    5. Returns the full PartnerInvite row
  On success: setInvite(data)
  On error: setError('Failed to create invite. Please try again.')
  setLoading(false)

PART 8 — JOINING WITH A CODE (INSIDE PARTNER PAGE)
================================================================================

When the user enters a code and taps "Join":

handleJoinWithCode() runs. The code is uppercased and trimmed first.

--- STEP 1: LOOK UP A MODERN INVITE TOKEN ---

  getInviteByShortCode(code):
    SELECT * FROM partner_invites
    WHERE short_code = code (uppercase)
      AND status = 'pending'
    LIMIT 1 (maybeSingle)

  Returns: PartnerInvite or null

--- BRANCH A: NO MODERN INVITE FOUND (legacy invite_code fallback) ---

  Fall back to looking up the users table directly (legacy path):
    SELECT * FROM users WHERE invite_code = code

  Validation checks (each returns early with setLinkError if fails):
    a. No user found:
         setLinkError('Invalid code. Please check and try again.')
    b. Partner is the user themselves (partner.id === user.id):
         setLinkError('You cannot link to yourself.')
    c. Partner already has a partner (partner.partner_id is not null):
         setLinkError('This user is already connected with someone else.')

  If all checks pass:
    UPDATE users SET partner_id = partner.id WHERE id = user.id
    UPDATE users SET partner_id = user.id   WHERE id = partner.id
    await onUpdate({ partner_id: partner.id })
      (updates global user state via useUser.updateUser)
    setPartnerCode('')
    setLinkSuccess(true)

--- BRANCH B: MODERN INVITE FOUND ---

  Call acceptInvite(invite, user.id):
    supabase.rpc('accept_partner_invite', {
      p_token: invite.token,
      p_joiner_id: user.id
    })
    Returns: { success: boolean, error?: string, inviter_id?: string }

  The RPC runs in SECURITY DEFINER mode and performs all of the following atomically:
    1. Validates invite is pending and not expired
    2. Validates inviter.id !== joiner.id (no self-join)
    3. Validates inviter has no existing partner
    4. Validates joiner has no existing partner
    5. Marks invite as accepted: UPDATE partner_invites SET status='accepted', invitee_id=joiner
    6. Links both users bidirectionally:
         UPDATE users SET partner_id=joiner.id WHERE id=inviter.id
         UPDATE users SET partner_id=inviter.id WHERE id=joiner.id
    7. Returns { success: true, inviter_id: inviter.id }

  If result.success=false:
    setLinkError(result.error)
    Return (do nothing further)

  If result.success=true:
    await onUpdate({ partner_id: invite.inviter_id })
    setPartnerCode('')
    setLinkSuccess(true)

--- ON ANY THROWN EXCEPTION ---

  setLinkError('Failed to link partner. Please try again.')

--- ALWAYS (finally block) ---

  setLinking(false)

PART 9 — UNLINKING A PARTNER
================================================================================

When the user taps "Unlink Partner":
  onRemovePartner() callback is called.
  This runs removePartner() from useUser hook.

removePartner() does ALL of the following in sequence:

  1. Remove partner link from partner's row:
     UPDATE users SET partner_id = null WHERE id = user.partner_id

  2. Remove partner link from user's own row:
     UPDATE users SET partner_id = null WHERE id = user.id

  3. Delete ALL matches for this couple:
     DELETE FROM matches
     WHERE user_a_id = user.id OR user_b_id = user.id
     (Removes matches for BOTH parties — they share the matches table)

  4. Update local React state:
     setUser({ ...user, partner_id: null })
     (Immediate UI update — page re-renders to the "unconnected" state)

IMPORTANT: There is NO confirmation dialog before unlinking.
The button tap directly triggers the unlink.
This means users can accidentally unlink their partner.
All shared matches are permanently deleted when this happens.
The partner will also see their partner_id cleared the next time they reload.

  If invite found:
    Also fetch inviter's display_name:
      SELECT display_name FROM users WHERE id = invite.inviter_id LIMIT 1

================================================================================
PART 11 — THE ACCEPT_PARTNER_INVITE RPC (FULL SPEC)
================================================================================

Function name: accept_partner_invite
Language: plpgsql
Security: SECURITY DEFINER (bypasses RLS to update both user rows)
Search path: public (explicit, for security)
Callable by: anon, authenticated

Parameters:
  p_token   text  — the full URL token from partner_invites.token
  p_joiner_id uuid — the user ID of the person accepting the invite

Returns: JSONB

Validation sequence (each failure returns { success: false, error: "..." }):
  1. Fetch invite WHERE token=p_token AND status='pending' AND expires_at > now()
     If not found: 'This invite link is invalid or has already been used.'
  2. If invite.inviter_id = p_joiner_id: 'You cannot join your own invite.'
  3. Select inviter's partner_id. If not null: 'This invite is no longer available.'
  4. Select joiner's partner_id. If not null: 'You are already connected with a partner.'

On all checks passing:
  UPDATE partner_invites SET status='accepted', invitee_id=p_joiner_id WHERE id=invite.id
  UPDATE users SET partner_id=p_joiner_id WHERE id=invite.inviter_id
  UPDATE users SET partner_id=invite.inviter_id WHERE id=p_joiner_id
  RETURN { success: true, inviter_id: invite.inviter_id }

Critical property: ALL three UPDATE statements run in the same transaction.
If any of them fails, all are rolled back (standard plpgsql block behavior).

================================================================================
PART 12 — THE PARTNER_INVITES TABLE
================================================================================

Full schema:

  id          uuid         PK, gen_random_uuid()
  token       text         UNIQUE NOT NULL — 48 hex chars, URL-safe, hard to guess
  short_code  text         UNIQUE NOT NULL — 8 uppercase alphanumeric chars
  inviter_id  uuid         NOT NULL, FK → users.id ON DELETE CASCADE
  invitee_id  uuid         NULLABLE, FK → users.id ON DELETE SET NULL
  status      text         NOT NULL DEFAULT 'pending'
                           CHECK ('pending', 'accepted', 'expired')
  created_at  timestamptz  DEFAULT now()
  expires_at  timestamptz  DEFAULT now() + interval '7 days'

Indexes:
  partner_invites_token_idx      ON token
  partner_invites_short_code_idx ON short_code
  partner_invites_inviter_id_idx ON inviter_id

RLS Policies:
  SELECT — "Inviter can view own invites":
    TO authenticated, anon
    USING inviter_id = (SELECT id FROM users WHERE id = auth.uid() LIMIT 1)

  SELECT — "Anyone can read pending invites":
    TO authenticated, anon
    USING status='pending' AND expires_at > now()
    (Needed so anyone can look up a token or short_code without being authenticated)

  INSERT — "Inviter can create invites":
    TO authenticated, anon
    WITH CHECK inviter_id IN (SELECT id FROM users WHERE id = inviter_id)

  DELETE — "Inviter can delete own pending invites":
    TO authenticated, anon
    USING inviter_id = (SELECT id FROM users WHERE id = inviter_id LIMIT 1)

  UPDATE — "Allow updating invite status":
    TO authenticated, anon
    USING status='pending' AND expires_at > now()
    WITH CHECK status IN ('accepted', 'expired')

One-invite-at-a-time rule: createInvite() expires all previous pending invites
before creating a new one. This means a user always has at most one active invite.

================================================================================
PART 13 — RELEVANT USERS TABLE COLUMNS
================================================================================

public.users relevant columns for partner linking:

  partner_id   uuid  nullable   FK → users.id  — points to the linked partner
  invite_code  text  unique     Legacy 8-char random code. Still used as fallback.
                                Format: Math.random().toString(36).substring(2,10).toUpperCase()
                                Example: "K4X9QMZR"

The partner relationship is BIDIRECTIONAL:
  If user A has partner_id = B.id, then B must have partner_id = A.id.
  This invariant is maintained by always updating both rows in the same operation.

If either user's row is deleted, the other's partner_id is automatically
set to NULL via ON DELETE SET NULL (foreign key behavior).

PART 14 — GUEST DATA MERGE (POST-AUTH)
================================================================================

When a guest user signs in via Google or magic link, their guest data is merged
into their authenticated account:

mergeGuestData(guestUserId, authUserId) is called from finalizeLogin() in authService.ts.
It is called only when localStorage('baby_picker_user_id') differs from the auth user ID.

Three sub-operations run in sequence:

  mergeSwipes(guestUserId, authUserId):
    SELECT name_id, liked FROM swipes WHERE user_id=guestUserId
    SELECT name_id FROM swipes WHERE user_id=authUserId
    Filter: only insert guest swipes whose name_id is not already swiped by auth user
    INSERT INTO swipes (user_id=authUserId, name_id, liked) for each filtered row

  mergeMatches(guestUserId, authUserId):
    UPDATE matches SET user_a_id=authUserId WHERE user_a_id=guestUserId
    UPDATE matches SET user_b_id=authUserId WHERE user_b_id=guestUserId
    (Reassigns all matches from guest ID to auth ID)

  mergeProfileSettings(guestUserId, authUserId):
    Reads both profiles.
    Only writes to authUserId row if the auth profile is missing data:
      display_name:        copy if auth has none but guest has one
      baby_last_name:      copy if auth has none but guest has one
      baby_gender:         copy if guest has a non-'either' preference
      partner_id:          copy if auth has no partner but guest does
      invite_code:         copy if auth has no invite_code
      onboarding_complete: copy if auth hasn't completed
      plan_tier:           copy if auth has no plan tier

After merge: localStorage('baby_picker_user_id') is set to authUserId.
The guest user row in public.users is NOT deleted — it just becomes orphaned.

PARTNER LINK DURING MERGE:
If the guest user had linked with a partner before signing in, that partner_id
is carried over to the auth account. This means the guest's partner connection
is preserved through authentication. This is the intended behavior — a user who
linked via a code while in guest mode retains that link after creating an account.

PART 15 — CONSIDERATIONS & EDGE CASES
================================================================================

1. INVITE LINK ON DESKTOP
   The invite link works on desktop browsers. When the invited person opens
   it on desktop, JoinView renders correctly. If they have no existing
   baby_picker_user_id in localStorage, a new user row is created automatically
   before the invite is accepted.

2. INVITE LINK WHEN ALREADY CONNECTED
   The RPC check #4 (joiner's partner_id IS NOT NULL) returns an error.
   The JoinView shows the error phase with the RPC error message.

3. EXPIRED INVITE LINK
   The query in getInviteByToken filters: AND expires_at > now()
   If the link is older than 7 days, getInviteByToken returns null.
   JoinView shows the invalid phase: "This invite link is invalid or has already been used."

4. INVITE CODE VS INVITE TOKEN
   The app has TWO separate linking mechanisms:
   a. Legacy invite_code on the users table (8-char random string).
      Still works as fallback if no modern invite token is found.
   b. Modern partner_invites table with a secure token (48 hex chars) and
      a short code (8 uppercase alphanum, no ambiguous chars).
   When a user enters a code, the app tries the modern system first.
   If not found, it falls back to the legacy users.invite_code lookup.

5. AFTER LINKING, MATCH DETECTION BEGINS IMMEDIATELY
   Once both users have partner_id set, every new like they make checks
   if the partner has also liked that name and creates a match row if so.
   There is NO retroactive match check — names liked BEFORE linking are
   not compared. Only future swipes create matches.
   IMPORTANT CONSIDERATION: If both users have already been swiping before
   linking, their pre-link likes will never become matches. A retroactive
   match-checking step after partner linking would improve the experience
   but does not currently exist.

6. UNLINK CLEARS ALL MATCHES
   removePartner() deletes ALL matches where user_a_id=me OR user_b_id=me.
   This affects the partner's view too — they will also see their matches
   disappear on next load. There is no soft-delete or per-user visibility.
   IMPORTANT CONSIDERATION: The lack of a confirmation dialog on Unlink Partner
   means this is destructive with no warning. A confirmation dialog is recommended.

7. THE SHARED MATCHES REALTIME CHANNEL
   When the user is viewing the Shared Matches tab, a Supabase Realtime
   subscription watches the matches table for this couple. This means:
   - When user A swipes and creates a match, user B sees it appear in real-time.
   - When user A unlinks (deletes matches), user B's list clears in real-time.
   The channel filter covers both user_a_id=me and user_b_id=me.

8. MULTIPLE PENDING INVITES
   createInvite() expires all previous pending invites before creating a new one.
   So if a user regenerates an invite (taps "Invite Partner" again), the old link
   and code immediately become invalid. The partner should use the newest link/code.

9. NO EMAIL NOTIFICATION TO PARTNER AFTER LINKING
   When the partner accepts the invite and the connection is made, there is no
   push notification or email sent to the original inviter to let them know.
   The inviter will only discover the connection when they return to the Partner
   page and see the connected state, or if they navigate to Shared Matches.

10. GUEST USER SECURITY NOTE
    The SECURITY DEFINER RPC is granted to the 'anon' role because guest users
    who are not authenticated still need to accept invites. This is intentional.
    All safety checks (expiry, self-join, existing partners) are enforced inside
    the function to compensate for the elevated privilege.
