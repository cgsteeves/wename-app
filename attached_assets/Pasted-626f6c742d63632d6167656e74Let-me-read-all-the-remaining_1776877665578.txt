SECTION 1 — USER IDENTITY SYSTEM
================================================================================

WeName uses a two-layer identity model: a persistent guest identity and an
optional authenticated identity. Both are backed by rows in the public.users
table in Supabase.

--- GUEST (ANONYMOUS) USERS ---

On first launch, if no user ID is found in storage, the app automatically
creates a new row in public.users with no email, no display_name, and a randomly
generated invite_code. The resulting UUID is immediately saved to
SecureStore (key: "baby_picker_user_id"). This happens silently with no user
interaction required.

From this point forward, all swipes, matches, and settings are tied to this UUID.
The user can swipe, rank, and configure everything as a guest. Data is fully
functional but only exists as long as the device retains the stored ID.

When a guest user's stored ID is found but no matching row exists in public.users,
a new guest row is created (this handles data loss scenarios).

--- AUTHENTICATED USERS ---

When a user signs in (via Google, Apple, or email magic link), the auth.users.id
from Supabase Auth becomes the canonical identity. After sign-in:

1. A row is upserted into public.users using the auth ID (never a new random UUID).
2. If a guest session was active (stored ID differs from auth ID), guestDataMerge
   runs to transfer all swipes, matches, and profile fields to the new auth ID.
3. The auth user ID overwrites the stored ID in SecureStore.

After this, the guest row is no longer referenced (it is not deleted, but it
becomes orphaned).

--- INVITE CODE ---

Every public.users row has a unique invite_code field (8 uppercase alphanumeric
characters, generated with Math.random().toString(36)). This code is used as
a fallback partner linking method when the full invite link is not available.
The invite_code is generated at row creation time and never changes.

--- USER FIELDS ---

id:                   UUID (from auth.users or randomly generated for guests)
email:                nullable, set on authentication
display_name:         nullable, set by user in Profile settings
baby_last_name:       nullable, shown alongside names during swiping
baby_gender:          'boy' | 'girl' | 'either' — controls which names appear
partner_id:           nullable UUID, references another public.users.id
invite_code:          8-char uppercase string, never null after creation
onboarding_complete:  boolean, set to true after tutorial is finished
plan_tier:            'free' | 'premium' — controls daily limits
daily_swipe_count:    integer, reset daily
daily_like_count:     integer, reset daily
daily_match_count:    integer, reset daily
usage_last_reset_at:  timestamp, used to determine if daily reset is needed

SECTION 3 — SWIPE SYSTEM
================================================================================

--- LOADING NAMES ---

On mount and whenever user.baby_gender or user.partner_id changes, the app
loads the swipe deck:

Step 1: Fetch all existing swipe records for this user from public.swipes
  (select name_id only) to build a set of already-swiped name IDs.

Step 2: Call getSwipeableNames(userId, gender):
  This calls the Supabase RPC function get_swipeable_names with:
    pack_slugs: the user's selected name packs (from user_selected_packs table)
    gender_filter: 'boy', 'girl', or null (for 'either')
  Returns an array of Name objects.

Step 3: If user has a partner_id, also call get_partner_created_names RPC:
  This returns names that the partner manually added to their liked list
  (names with created_by_user_id = partner_id). These are special "partner picks"
  that appear in the deck so the current user can swipe on them.

Step 4: Filter out already-swiped names from the catalog.
  If all names have been swiped, use the full unfiltered catalog anyway
  (so the user always has something to swipe on).

Step 5: Shuffle the combined catalog.
  For 'either' gender: interleave boy and girl names alternately (not random)
  to ensure variety. Both sub-lists are individually shuffled first.
  For single gender: random shuffle.

Step 6: Set names array and currentIndex = 0.

--- CARD STACK ---

At most 2 cards are rendered simultaneously:
  currentName = names[currentIndex]     → front card (interactive)
  nextName    = names[currentIndex + 1] → back card (decorative, no interaction)

The back card is pre-rendered so it appears instantly after a swipe.

--- SWIPING ---

When the user swipes or taps a button:

1. Limit check (BEFORE any DB write):
   Call checkCanSwipe(liked) from useDailyLimits hook.
   If not allowed:
     - Show PremiumUpgradeModal with the appropriate limitType.
     - ABORT the swipe — nothing is written to the DB.
     - The card does not advance.
   If allowed:
     - Increment daily_swipe_count (and daily_like_count if liked) in DB.
     - Proceed.

2. Update local state:
   - Add to swipeHistory: { nameId: currentName.id, liked }
   - Advance currentIndex by 1.
   - Reset dragProgress to 0.

3. Write to DB (async, non-blocking):
   Upsert into public.swipes:
     { user_id, name_id: currentName.id, liked }
   onConflict: 'user_id,name_id' (if user swipes the same name twice, update)

4. If liked AND user has a partner_id:
   Call checkForMatch(currentName).

5. First-like check:
   If liked AND SecureStore key "first_like_partner_shown_{userId}" is not set:
     - Set the key to "1".
     - Show the FirstLikePartnerModal.

--- MATCH CHECKING ---

Called after every like when partner_id is set:

1. Query public.swipes for a row where:
     user_id = partner_id
     name_id = currentName.id
     liked = true
   Use maybeSingle() — no error if not found.

2. If partner has liked the same name:
   a. Sort [user.id, partner_id] alphabetically → [userA, userB].
   b. Insert into public.matches:
        { name_id, user_a_id: userA, user_b_id: userB, gender: name.gender }
   c. Call checkCanRevealMatch():
        If allowed (within daily limit): set matchedName state → show match modal.
        If blocked: show PremiumUpgradeModal with limitType = 'match'.
        The match IS saved to DB in both cases — only the notification is gated.

--- UNDO ---

Available when swipeHistory.length > 0 AND currentIndex > 0.

Steps:
1. Get lastSwipe from swipeHistory.
2. Delete the swipe from public.swipes:
     WHERE user_id = user.id AND name_id = lastSwipe.nameId
3. If lastSwipe.liked AND partner_id:
   Delete the potential match from public.matches:
     WHERE name_id = prevName.id AND user_a_id = sorted[0] AND user_b_id = sorted[1]
4. Remove last item from swipeHistory.
5. Decrease currentIndex by 1.

--- MATCH CELEBRATION MODAL ---

When matchedName is set, a full-screen modal appears with:
  - The matched name displayed large
  - A bouncing heart animation
  - Optional last name display

The modal auto-dismisses after 4000ms via setTimeout, or immediately when
the user taps "Keep Swiping".

--- EMPTY AND ERROR STATES ---

If names array is empty after loading: show "All done!" with a "Start Over"
button that calls loadNames(includeAlreadySwiped = true).

If loading throws: show error message with "Try Again" button.

--- PARTNER PICKS ---

Names returned by get_partner_created_names are flagged with isPartnerPick=true.
These names show a "Partner Added" badge on the card. When swiped right on,
they trigger match checking immediately (since the partner already "liked" them
by adding them manually).

SECTION 4 — DAILY LIMITS SYSTEM (useDailyLimits)
================================================================================

Applies to FREE users only. Premium users (plan_tier = 'premium') bypass all
limits — checkCanSwipe and checkCanRevealMatch always return allowed=true.

Free limits per calendar day:
  Swipes:         30
  Likes:          8   (a like also counts as a swipe — both counters increment)
  Match reveals:  3

--- DAILY RESET ---

Before any limit check, the hook compares today's date (YYYY-MM-DD in local
timezone) against the date portion of user.usage_last_reset_at.

If they differ (or if usage_last_reset_at is null):
  - Set daily_swipe_count, daily_like_count, daily_match_count to 0 in DB.
  - Set usage_last_reset_at to current timestamp.
  - Call updateUser() to sync local state.
  - Use the reset counts (all 0) for the current check.

A resetInFlight ref prevents concurrent reset calls.

--- checkCanSwipe(liked: boolean) ---

Returns: { allowed: boolean, limitType: 'swipe' | 'like' | null }

Logic:
  1. Run daily reset if needed.
  2. If swipe_count >= 30: return { allowed: false, limitType: 'swipe' }
  3. If liked AND like_count >= 8: return { allowed: false, limitType: 'like' }
  4. Otherwise: increment swipe_count (+1) and like_count (+1 if liked) in DB,
     call updateUser, return { allowed: true, limitType: null }

--- checkCanRevealMatch() ---

Returns: boolean

Logic:
  1. Run daily reset if needed.
  2. If match_count >= 3: return false
  3. Otherwise: increment match_count (+1) in DB, call updateUser, return true

--- PARTNER INVITE FLOW (SENDER) ---

Only available to authenticated users. If user is a guest, tapping "Invite Partner"
triggers the auth flow first (via AuthModal). On successful auth, the pending
invite action completes automatically (tracked via pendingInviteRef).

InvitePartnerView:
  On mount: calls createInvite(userId):
    1. Marks all existing pending invites from this user as 'expired' in
       public.partner_invites (UPDATE status = 'expired' WHERE inviter_id = userId
       AND status = 'pending').
    2. Generates a cryptographically random 48-char hex token (24 bytes via
       crypto.getRandomValues).
    3. Generates an 8-char uppercase alphanumeric short code (avoiding ambiguous
       chars like 0/O, 1/I).
    4. Inserts into public.partner_invites:
         { token, short_code, inviter_id: userId, status: 'pending' }
    5. Returns the invite record.

  The invite URL is: {appOrigin}/join/{token}
  (In React Native: wename://join/{token} or https://wename.app/join/{token})

  Display:
    - Full URL shown in a read-only field with a Copy button.
    - Short code shown large with a Copy button.
    - "Share Invite Link" button triggers native share sheet with the URL and
      a pre-written message.
    - Footer note: "This link and code expire in 7 days."

--- PARTNER INVITE FLOW (RECEIVER — VIA LINK) ---

When the app is opened via a /join/{token} deep link, JoinView renders.

States: loading → confirm → joining → success / error / invalid

VALIDATE: getInviteByToken(token):
  Query public.partner_invites WHERE token = token AND status = 'pending'.
  If not found: show "Link not valid" state.
  If found: fetch inviter's display_name. Show "confirm" state.

JOIN (handleJoin):
  1. Ensure a user ID exists in storage. If not, create a new guest user row.
  2. Call acceptInvite(invite, userId):
     This calls the Supabase RPC accept_partner_invite with:
       p_token: invite.token
       p_joiner_id: userId
     The RPC (server-side) handles:
       - Validating the token is still pending and not expired.
       - Setting user_a.partner_id = user_b.id and user_b.partner_id = user_a.id.
       - Marking the invite as 'accepted'.
     Returns { success: boolean, error?: string, inviter_id?: string }
  3. If success: update local user state with { partner_id: invite.inviter_id }.
     Show "You're connected!" success state.
  4. If error: show error state with "Try again" button.

--- PARTNER INVITE FLOW (RECEIVER — VIA CODE) ---

In the Partner settings page, the "Join with code" section:
  User enters an 8-char code. On submit (handleJoinWithCode):

  Step 1: Try getInviteByShortCode(code):
    Query public.partner_invites WHERE short_code = code AND status = 'pending'.

  Step 2a: If invite found:
    Call acceptInvite(invite, user.id) — same RPC as link flow.
    On success: call onUpdate({ partner_id: invite.inviter_id }), show success.

  Step 2b: If no invite found:
    Fall back to legacy invite_code lookup:
    Query public.users WHERE invite_code = code.
    Validate: partner must exist, must not be the current user, must not already
    have a partner.
    If valid: directly update both user rows:
      UPDATE users SET partner_id = partner.id WHERE id = user.id
      UPDATE users SET partner_id = user.id WHERE id = partner.id
    Call onUpdate({ partner_id: partner.id }), show success.

  Errors shown inline:
    "Invalid code. Please check and try again."
    "You cannot link to yourself."
    "This user is already connected with someone else."
    "Failed to link partner. Please try again."

--- REMOVING A PARTNER ---

In Partner settings page, "Unlink Partner" button calls removePartner():
  1. UPDATE public.users SET partner_id = null WHERE id = partner.id
  2. UPDATE public.users SET partner_id = null WHERE id = user.id
  3. DELETE FROM public.matches WHERE user_a_id = user.id OR user_b_id = user.id
     (ALL match history is deleted when partners unlink)
  4. Update local user state: partner_id = null.

SECTION 7 — AUTHENTICATION
================================================================================

--- AUTH FLOWS ---

GOOGLE OAUTH:
  Calls supabase.auth.signInWithOAuth({ provider: 'google' })
  with redirectTo pointing to the app's auth callback URL.
  The browser (or in-app WebView) opens Google's auth page.
  After approval, Supabase redirects back with session tokens.
  In React Native: use expo-auth-session with makeRedirectUri({ scheme: 'wename' }).

EMAIL MAGIC LINK:
  POSTs to Supabase Edge Function /functions/v1/send-magic-link:
    Body: { email, redirectTo: '{origin}/auth/callback' }
  The Edge Function uses Supabase Admin API to generate a magic link and sends
  it via SendGrid as a branded email.
  User clicks link → auth callback page → session established.
  Magic links expire after 1 hour.

AUTH CALLBACK:
  After any successful auth, the /auth/callback handler (web) or deep link
  handler (wename://auth/callback in native) calls finalizeLogin(userId, email):
    1. Upsert into public.users: { id: userId, email, updated_at: now() }
    2. If display_name not already set, check auth user metadata for full_name.
    3. If invite_code not set, generate one.
    4. If a different guest ID was in storage, call mergeGuestData(guestId, authId).
    5. Save auth user ID to SecureStore key "baby_picker_user_id".

POST-AUTH REDIRECT:
  Before opening auth, certain actions set a "post_auth_redirect" value in
  storage (e.g., "partner"). After successful auth, this value is consumed
  and the appropriate action is taken (e.g., navigating to the partner invite view).

SIGN OUT:
  Calls supabase.auth.signOut(). This clears the session.
  The app falls back to guest mode — a new guest user row will be created on
  next app launch if the stored ID is no longer valid.
  Guest data from before sign-in is NOT retained after sign-out
  (user.id was changed to auth ID during login).

DELETE ACCOUNT:
  Requires active session. POSTs to /functions/v1/delete-account with the
  user's access token. The Edge Function:
    - Deletes the public.users row.
    - Deletes the auth.users entry via Admin API.
    - Deletes all related data (swipes, matches, finalists).
  After success: removes stored ID from SecureStore, calls signOut().

--- AUTH STATE ---

AuthContext subscribes to supabase.auth.onAuthStateChange. On SIGNED_IN or
USER_UPDATED events, if the user has an email, upserts { id, email } into
public.users as a lightweight backstop.

isAuthenticated is true whenever session is not null.

--- GUEST DATA MIGRATION (mergeGuestData) ---

Called after login if stored guest ID differs from auth user ID.

1. mergeSwipes:
   - Fetch all guest swipes (name_id, liked).
   - Fetch all auth user swipes (name_id).
   - Insert guest swipes that don't already exist for the auth user.
   - Names the auth user already swiped are NOT overwritten.

2. mergeMatches:
   - UPDATE matches SET user_a_id = authId WHERE user_a_id = guestId
   - UPDATE matches SET user_b_id = authId WHERE user_b_id = guestId

3. mergeProfileSettings:
   - Fetch guest profile fields.
   - Fetch auth profile fields.
   - For each field (display_name, baby_last_name, baby_gender, partner_id,
     invite_code, onboarding_complete, plan_tier):
     Only copy from guest if auth profile field is null/empty.
   - Exception: baby_gender is copied only if guest value is not 'either'
     (i.e., if the guest set a specific preference).

  - If pack is already selected: do nothing (can't deselect without selecting another).
  - Otherwise: call setUserPack(userId, pack.slug):
      1. DELETE FROM public.user_selected_packs WHERE user_id = userId
         (removes all current selections)
      2. INSERT INTO public.user_selected_packs { user_id, pack_slug }
    Update local selectedSlugs state to reflect only the new selection.

DEFAULT PACK: 'top_2000' (constant DEFAULT_PACK_SLUG).
  If no selection exists for a user, getSwipeableNames treats 'top_2000' as default.

SECTION 9 — FIRST-LIKE PARTNER MODAL
================================================================================

Triggered once, the first time a user swipes right on any name.

TRIGGER CONDITION:
  In handleSwipe, after a successful like:
  Check SecureStore key "first_like_partner_shown_{userId}".
  If NOT set:
    - Set the key to "1".
    - Set showPartnerModal = true.

MODAL BEHAVIOR:
  If user already has a partner (user.partner_id is set):
    Shows "Keep Swiping" button. Modal is informational only.

  If user does NOT have a partner:
    Shows "Invite Partner" button.
    If user is authenticated: closes modal, navigates to partner invite view.
    If user is NOT authenticated:
      - Sets post_auth_redirect = 'partner'.
      - Sets pendingInviteRef = true.
      - Shows AuthModal with partner-invite-specific text.
      On successful auth:
        - Closes AuthModal.
        - Closes partner modal.
        - Navigates to partner invite view.

  "Maybe later" button simply closes the modal.
